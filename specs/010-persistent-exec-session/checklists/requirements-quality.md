## Requirement Completeness

- [ ] CHK001 Are requirements defined for what happens when the bridge process itself is down at engagement time (not just resume-target-gone)? [Gap] — **DEFERRED — v1 relies on the existing transport failure path.** A down bridge already surfaces as a non-zero `ask.sh`/curl status that the runner reports; a mandate adds no new *silent* failure mode (the engagement is recorded `failed`, no thread is written). No new FR invented. Carried as part of plan.md risk **R-E**'s post-v1 follow-up.
- [ ] CHK002 Is a requirement stated for what `mandate list --json` output shape is, beyond the human-readable line format? [Gap, Spec §C2] — **ACCEPTED — shape is the record itself.** contracts C2 specifies the human line format normatively and `--json` as a dump of the same Mandate record already fully specified in `data-model.md`; no second schema is needed, and `mandate show --json` (same record) is what tests and quickstart read. Pinning a distinct `list --json` envelope would add a contract with no consumer in v1.
- [ ] CHK003 Are requirements defined for concurrent `mandate close` calls racing a fresh `submit --mandate` on the same `run_id`? [Gap, Coverage] — **DEFERRED — real gap, knowingly out of v1.** The store is `tmp+rename` atomic per write, but `engage()`'s read-modify-write is unlocked, so a close racing a submit (or two submits) can lose an engagement. Accepted for v1 because scope is a single operator on one machine (plan Technical Context "Scale/Scope") and both outcomes are fail-closed (nothing resumes a wrong thread). Follow-up carrier: plan.md risk **R-E** (file-lock protocol around `engage()`/`close`), analyze pass-2 W-14 disposition.

## Scenario Coverage

- [ ] CHK011 Are requirements defined for the Alternate flow where a Supervisor pulls in a free-model role under the same mandate (US2 scenario 3) and that role's dispatch fails outright (not just "recorded")? [Coverage, Gap, Spec §US2] — **ACCEPTED — covered by the existing engagement-outcome model, no new FR.** A failed dispatch of any role is an Engagement with `outcome = failed` (data-model.md Engagement) and `in_flight_job_id` cleared; FR-010 requires every dispatch record to state fresh-vs-resumed, and FR-011 fixes `continuity = no-resume` for non-Codex roles. Nothing about a free-model role's failure is special to this feature.
- [ ] CHK012 Are Exception-flow requirements defined for a malformed/corrupted mandate JSON file on disk (not just "provider purged the session")? [Coverage, Gap, Edge Case] — **DEFERRED — genuine gap, knowingly accepted for v1.** v1 behaviour is an unhandled decode error surfacing as a non-zero exit: fail-closed (no silent wrong resume, no write over the damaged file), which is the safe direction. An explicit refusal with a dedicated exit code is a **post-v1 follow-up** carried by plan.md risk **R-E** alongside the locking work (analyze pass-2 W-14). Flagged to the operator as an accepted v1 limitation rather than a silently invented FR-016.
- [ ] CHK013 Are Recovery-flow requirements defined for what the caller should do after an FR-008 resume failure, beyond "explicit fresh restart" — e.g. is the old thread's engagement history discoverable afterward? [Coverage, Spec §FR-008] — **ACCEPTED — discoverability is already required by the record shape.** The stale thread is preserved (`replaced_thread_ids`, appended on `--fresh`; data-model.md state transitions keep `thread_id` on `resume-failed`), the failed engagement stays in the append-only `engagements` list with `outcome = resume-failed`, and `mandate show` exposes both. The caller-facing recovery instruction is the exit-9 stderr string itself ("rerun with `--fresh` to replace", C1).

## Edge Case Coverage (spec.md `### Edge Cases`, individually)

- [ ] CHK014 Resume-target-gone: is the required caller-visible signal (409 vs. some other status) specified in spec.md itself, or only in contracts/plan? [Completeness, Spec §Edge Cases] — **ACCEPTED — correct layering.** spec.md states the *requirement* (FR-008: report the failure, never silently substitute; edge case "surface, do not silently cold-start"); the wire-level signal (HTTP 409, exit 9, exact stderr) is an interface detail that belongs in contracts C1/C3 by design, and is checked there (CHK007/CHK009 of `implementation-readiness.md`). - [ ] CHK015 Caller-process-dies-mid-mandate: does spec.md specify who is authorized to act as the "new run root" (any process, or the same Task Authority holder)? [Gap, Spec §Edge Cases] — **DEFERRED — same class as W-05's authentication gap, not closable by wording.** v1 has **no caller authentication of any kind** (FR-005a's residual-risk line says so explicitly), so any process with filesystem access to the state dir can act as the new run root. - [x] CHK016 Vendor-without-resume: is the exact continuity value (`no-resume`) and its non-negotiability (never silently claims persistence) stated as a MUST in spec.md, not just contracts? [Consistency, Spec §Edge Cases, §FR-011] — **RESOLVED — FR-011 states both as MUSTs.** As rewritten it reads "MUST record `continuity = no-resume` **and** MUST NOT claim the underlying path is stateless", in spec.md itself; data-model.md I4 and the `continuity` field make it a test target (T004/T008).
- [ ] CHK017 Two-concurrent-mandates-same-role: is "keyed by mandate, never shared" testable independent of implementation, i.e. does spec.md give an observable signal (distinct thread_ids) rather than an internal-only guarantee? [Measurability, Spec §Edge Cases] — **ACCEPTED — observable signal exists.** The keying is observable through `mandate show <run_id> --json`, whose `roles.<r>.thread_id` must differ between two mandates using the same role and model; that is what `test_new_mandate_same_roles_gets_fresh_session_no_leak` (T022) and `implementation-readiness.md` CHK016 assert. The signal is a CLI output, not an internal attribute.
- [x] CHK018 Mandate-never-closed: is the 7-day threshold justified/owned as a product decision in spec.md (Clarifications Q5) rather than an arbitrary engineering constant? [Traceability, Spec §Clarifications Q5] — **RESOLVED — owned by the operator.** FR-013 carries `[Clarifications Q5=B]`, and the Clarifications section records the operator's answer ("never auto-close; session-start / preflight lists open mandates older than 7 days as a warning"). - [x] CHK019 `--force` duplicate override: does spec.md specify what "both engagements recorded" means for downstream ledger consumers (e.g. does the ledger need a marker distinguishing the overridden pair)? [Gap, Spec §Edge Cases] — **RESOLVED — no ledger consumer exists in v1, by ruling.** research R5 was **struck** (first fix pass, warning (e)): `mandate close` and mandate dispatch write **nothing** to the ledger, which is read-only context for this feature, and tasks.md's scope guard forbids `workerbees/**` edits. Ledger emission is a named post-v1 follow-up.
